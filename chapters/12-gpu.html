12Parallelisation on GPUs

Why explicit DG is a natural fit for graphics hardware: thousands of threads, element-local work, race-free face fluxes — and a live WebGPU solver you can run in this page.

A graphics card shades millions of pixels per frame by running the same small program on every pixel at once. A DG solver for a conservation law does something remarkably similar: at every time step it runs the same small computation on every node of every element, and elements talk to each other only through their faces. In this chapter we take a 2D DG advection solver (the method of chapter 6) apart into GPU kernels, look at what makes such kernels fast or slow (memory traffic, not arithmetic!), meet the classic pitfall of parallel assembly — the race condition — and finally run the solver on your GPU through WebGPU, checked number-by-number against a CPU twin.

Why GPUs? Latency versus throughput

A CPU core is built to finish one instruction stream as quickly as possible: deep pipelines, branch prediction, out-of-order execution and large caches all fight latency, the time until one result is ready. A GPU makes the opposite bet. It has thousands of simple arithmetic lanes and no attempt to make a single thread fast; instead it keeps a huge number of threads in flight and, whenever one group stalls on a memory access (hundreds of clock cycles), it switches — at no cost — to another group that is ready. The design maximises throughput, the number of results per second, at the price of latency.

The bet pays off when a problem offers massive, uniform parallelism: the same operation on millions of independent data items. Rendering is the original example (one fragment-shader invocation per pixel). Explicit time stepping of a DG or finite volume method is another: a mesh with $10^6$ degrees of freedom offers $10^6$ independent node updates per stage. As orders of magnitude, a current discrete GPU delivers tens of TFLOP/s (f32) and close to a terabyte per second of memory bandwidth, several times to ten times more than a CPU socket — if the algorithm feeds it properly. Most of this chapter is about what "properly" means.

Graphics analogy

A compute kernel is a fragment shader without the rasteriser. A fragment shader runs once per pixel, reads textures, and writes its own pixel; a compute kernel runs once per index $g = 0, 1, \dots$, reads storage buffers (think: textures you can index freely with integers) and writes wherever it wants — which is both more flexible and more dangerous (see races). The uniform buffer holding constants like the time step is exactly the uniform block of a shader.

The execution model: threads, warps, workgroups

In WebGPU's shading language WGSL, a compute kernel is a function marked @compute and launched ("dispatched") on a grid of workgroups. Each workgroup consists of a fixed number of threads (we use @workgroup_size(64)), and every thread learns its global index from the built-in global_invocation_id. To process $M$ items we launch $\lceil M/64\rceil$ workgroups; the last one may be partially empty, which is why every kernel begins with if (g >= M) { return; }.

Inside the hardware, the threads of a workgroup are executed in bundles of $W$ consecutive threads — warps (NVIDIA), wavefronts (AMD), subgroups (WebGPU/Vulkan). All lanes of a warp execute the same instruction at the same time on different data: SIMT, single instruction, multiple threads. This has a striking consequence for if statements. When some lanes of a warp take a branch and others do not, the warp executes the branch anyway, with the non-participating lanes masked off (idle); then it executes the other branch with the roles reversed. This is called divergence: the warp pays for both paths. Branches cost nothing extra only when all $W$ lanes agree.

Two quantities summarise the picture: the number of threads (parallelism) and the SIMT efficiency, the fraction of issued lane-slots that do useful work. One thread per DOF gives $N^2 N_p$ threads; one per element only $N^2$ — on a $64\times64$ mesh that is 4096 threads, too few to fill a GPU that wants tens of thousands in flight. That is why our kernels use one thread per DOF (and one per face node for the face kernel) and accept a little divergence in the lift kernel.

The memory hierarchy and latency hiding

Data lives at several levels, from small and fast to large and slow:

  • Registers: private to a thread, the fastest storage; a compute unit has a fixed register file shared by all resident threads.
  • Workgroup (shared) memory: tens of kilobytes per compute unit, shared by the threads of one workgroup, explicitly managed (var<workgroup> in WGSL, with workgroupBarrier() to synchronise). A typical use: load an element's values once, then let all its threads read them many times.
  • Caches (L1 per compute unit, L2 shared): automatic, they catch reuse such as neighbouring threads reading the same element.
  • Global memory (DRAM / HBM on the card): gigabytes, high bandwidth but a latency of hundreds of cycles per access. Our storage buffers live here.

How does a GPU stay busy while a warp waits hundreds of cycles for global memory? By having many other warps resident on the same compute unit, ready to run: latency hiding through parallelism. The ratio of resident warps to the hardware maximum is the occupancy. It is limited by resources: if each thread needs many registers, or each workgroup much shared memory, fewer warps fit, and latency is exposed. This is a recurring trade-off — a "smarter" kernel that keeps more in registers can be slower because it lowers occupancy.

Bandwidth versus FLOPs: the roofline model

Every kernel moves data and computes on it. Let a kernel perform $F$ floating-point operations and move $Q$ bytes between global memory and the chip. Its arithmetic intensity is $I = F/Q$ [FLOP/byte]. A device can do at most $P_\text{peak}$ FLOP/s and move at most $B$ byte/s, so the time is at least $\max(F/P_\text{peak},\, Q/B)$ and the attainable rate is

$$P \;\le\; \min\big(P_\text{peak},\; B\cdot I\big).$$

Plotted on log–log axes this is the roofline: a slanted line $B\cdot I$ (memory-bound) meeting a flat roof $P_\text{peak}$ (compute-bound) at the ridge point $I^* = P_\text{peak}/B$. For a generic modern GPU with 30 TFLOP/s and 800 GB/s, $I^* \approx 37$ FLOP/byte: a kernel must do 37 operations for every byte it touches to be limited by arithmetic.

Our kernels are far from that. The Runge–Kutta update $k \leftarrow A k + \Delta t\, r$, $u \leftarrow u + Bk$ does 5 FLOPs per DOF while reading three f32 values and writing two (20 bytes): $I = 0.25$. Even the volume kernel, which does $4n + 5$ FLOPs per DOF (two 1D derivatives of $n$ multiply–adds each) for 8 bytes, has $I \approx 2.6$ at $p=3$. Summed over one RK stage of four kernels we get about $0.68$ FLOP/byte at $p=3$. Explicit DG on a GPU is memory-bound: its speed is set by bytes, not FLOPs, so optimisations should reduce memory traffic.

Memory coalescing: AoS versus SoA

Global memory is not read value by value but in aligned segments (typically 32 to 128 bytes). When the $W$ threads of a warp load $W$ consecutive f32 values, the hardware merges ("coalesces") the requests into the minimum number of segments — one or a few wide transactions. When they load scattered values, each touched segment is transferred in full, and most of the bytes are thrown away. Since we are memory-bound, coalescing directly decides speed.

The data layout is what makes access consecutive. Take a system of PDEs with several fields per node (the Euler equations have four: $\rho$, $\rho u$, $\rho v$, $E$):

  • Array of structures (AoS): [ρ₀ ρu₀ ρv₀ E₀ ρ₁ ρu₁ …] — natural in object-oriented CPU code (an array of struct Node). When thread $t$ loads $\rho_t$, consecutive threads read addresses $4t$: stride 4, so a warp touches four times as many segments as needed.
  • Structure of arrays (SoA): [ρ₀ ρ₁ ρ₂ … | ρu₀ ρu₁ … | …] — one array per field. Thread $t$ reads address $t$: perfectly coalesced.

The thread mapping matters just as much. Our DOFs are stored element by element ($g = e N_p + jn + i$). With one thread per DOF, consecutive threads read consecutive $g$ — coalesced. With one thread per element, thread $e$ reads $u[e N_p + l]$: a stride of $N_p$, uncoalesced. (Advanced codes use hybrids such as "AoSoA" blocks, or stage an element's data through workgroup memory.)

Graphics analogy

Vertex buffers face the same choice: interleaved attributes (position, normal, uv per vertex: AoS) versus separate streams (SoA). Interleaving wins when one shader invocation reads all attributes of its vertex; separate streams win when consecutive invocations read the same attribute — which is the GPU-compute situation.

Why DG and FV map well to GPUs — and continuous FEM less so

Three properties make explicit DG (and finite volume, its $p = 0$ cousin from chapter 5) a near-perfect GPU workload:

  1. Element-local dense work. All volume computations of an element use only that element's $N_p$ values and small dense matrices ($D$, the reference operators). That is regular, branch-free, cache-friendly arithmetic.
  2. Coupling only through faces. Neighbours interact only via the numerical flux on shared faces, which needs the traces of two elements — a small, structured amount of data.
  3. Explicit time stepping with a diagonal mass matrix. With collocated GLL quadrature (or an orthonormal modal basis) the mass matrix is diagonal, so $\mathrm du/\mathrm dt = M^{-1} R(u)$ needs no linear solve: every stage is a handful of pointwise and element-local kernels.

Compare continuous finite elements (chapter 3). Their unknowns are shared between elements, so the classic assembly loop "for each element, compute the local vector and add it into the global vector" makes several threads add to the same global entry: a race condition (next section), which must be cured by colouring or atomics. Worse, CG methods for elliptic problems lead to large sparse linear systems. Solving them with the conjugate gradient method requires dot products in every iteration — global reductions over all threads, which need several kernel launches or synchronisation across the whole GPU — and the best preconditioners (incomplete factorisations, Gauss–Seidel) are inherently sequential. These problems can be solved (matrix-free operators, multigrid, polynomial smoothers), but they are research topics, whereas an explicit DG step is parallel out of the box.

Race conditions on face fluxes, and two classic cures

Suppose each thread handles one face and wants to add its flux contribution to both neighbouring elements, or each CG element-thread adds its local vector to the shared vertices. A "+=" on memory is really three steps: load the old value, add, store. If two threads load the same old value before either stores, one of the two updates is simply lost — a race condition. The result depends on timing, changes from run to run, and is wrong. Two classic remedies avoid any shared write:

  1. Face buffer + gather (what our solver does). A face kernel with one thread per face node computes the numerical flux and writes it into a slot of a face buffer that belongs to that face alone. A second kernel, one thread per DOF, gathers (reads) the fluxes of its own element's faces and writes only its own value. Every address has exactly one writer. Cost: an extra buffer and an extra kernel launch; each flux is computed once.
  2. Graph colouring. Colour the elements so that two elements sharing a vertex (or face) never have the same colour, then run one kernel launch per colour. Within a colour no two threads touch the same entry, so scatter-adds are safe. A structured quad mesh needs 4 colours for vertex sharing ($2\times2$ pattern); unstructured meshes need more, and each colour is a separate, smaller launch.

A third option is atomic operations, read–modify–write instructions that the hardware performs indivisibly. WGSL, however, has atomics only for 32-bit integers (atomic<i32>, atomic<u32>): there is no floating-point atomicAdd. One can emulate it with a compare-and-swap loop on the bit pattern (bitcast + atomicCompareExchangeWeak) or accumulate in fixed-point integers — both slow under contention — and even where float atomics exist (CUDA), the order of the additions varies from run to run, so results are no longer bitwise reproducible (floating-point addition is not associative).

Graphics analogy

The face buffer is a G-buffer pass, as in deferred shading: pass 1 writes intermediate per-face results into a dedicated buffer, pass 2 reads whatever it needs from it. The ping-pong buffers of our time stepper (read from $u^{(0)}$, write $u^{(1)}$, swap) are the double-buffered render targets of every GPU fluid or blur effect — you never sample the texture you are rendering into.

The solver: DG-SEM advection in four kernels

We solve $u_t + \mathbf a\cdot\nabla u = 0$ with constant velocity $\mathbf a = (a_x, a_y)$ on the periodic unit square, with the nodal DG spectral element method (DG-SEM): on each square element a tensor-product nodal basis of degree $p$ on the $(p+1)\times(p+1)$ GLL nodes, with quadrature collocated at the same nodes, so the mass matrix is diagonal, $M = \tfrac{h^2}{4}\operatorname{diag}(w_i w_j)$. (This "lumped" GLL mass matrix is not the exact one — GLL with $n$ points integrates exactly only up to degree $2p-1$ — but it is the standard, accurate DG-SEM choice.) The upwind flux through a face with normal $\mathbf n$ pointing from $K^-$ to $K^+$ is

$$\hat F(u^-, u^+) = \begin{cases} (\mathbf a\cdot\mathbf n)\,u^- & \mathbf a\cdot\mathbf n \ge 0,\\ (\mathbf a\cdot\mathbf n)\,u^+ & \mathbf a\cdot\mathbf n < 0.\end{cases}$$

Write $u_{ij}$ for the value at node $(\xi_i, \xi_j)$ of an element. Because the GLL differentiation matrix satisfies a discrete integration-by-parts (summation-by-parts) identity, the weak form of chapter 6 can be rewritten exactly in strong form:

$$\begin{aligned} \frac{\mathrm d u_{ij}}{\mathrm dt} \;=\; &-\frac{2}{h}\Big(a_x\sum_{k=0}^{p} D_{ik}\,u_{kj} \;+\; a_y\sum_{k=0}^{p} D_{jk}\,u_{ik}\Big) &&\text{(volume kernel)}\\ &-\frac{2}{h\,w_0}\sum_{\text{faces } f \ni (i,j)} \Big(\hat F_f^{\text{out}} - (\mathbf a\cdot\mathbf n_K)\,u_{ij}\Big) &&\text{(lift kernel)}. \end{aligned}$$

Here $\mathbf n_K$ is the outward normal of the element and $\hat F_f^{\text{out}}$ the flux out of the element through face $f$. The factor $2/h$ is the chain rule $\partial_x = \tfrac{2}{h}\partial_\xi$, and $\tfrac{2}{h w_0}$ is the face quadrature weight $\tfrac h2 w_m$ divided by the diagonal mass entry $\tfrac{h^2}{4} w_0 w_m$ ($w_0 = w_p = \tfrac{2}{p(p+1)}$ is the GLL end-point weight). Only the nodes on the element boundary receive face terms. With the upwind flux, $\hat F^{\text{out}} - (\mathbf a\cdot\mathbf n_K)u^- = \min(\mathbf a\cdot\mathbf n_K, 0)\,(u^+ - u^-)$: only inflow faces contribute, and only through the jump. In time we use the 5-stage, 4th-order low-storage Runge–Kutta method of Carpenter and Kennedy,

$$\text{for } s = 0,\dots,4:\qquad k \leftarrow A_s\,k + \Delta t\, L(u), \qquad u \leftarrow u + B_s\,k,$$

which needs only two arrays per DOF ($u$ and $k$) — on a GPU, memory is the scarce resource. The time step is $\Delta t = h/\big((|a_x| + |a_y|)(2p+1)\big)$; the test suite checks (on a $4\times4$ mesh, $p = 1,2,3$, several velocities) that every eigenvalue of the semi-discrete operator, scaled by this $\Delta t$ and even by $2\Delta t$, lies inside the stability region of the method.

Data layout and kernels

All arrays are flat f32 storage buffers, element-major: DOF $g = e N_p + j n + i$ with $e = e_y N + e_x$. The face buffer holds one value per face node; the face to the right of element $e$ owns slots $e n + m$, the face above it owns slots $N^2 n + e n + m$ — each periodic face is owned by exactly one element (its left or lower neighbour $K^-$), so the face kernel writes every slot exactly once. Sum factorisation: $O(p^{d+1})$ instead of $O(p^{2d})$


Look again at the volume term. The $x$-derivative of the nodal values of one element is a linear map from $N_p$ numbers to $N_p$ numbers, so one could
store it as an $N_p\times N_p$ matrix and multiply: $2N_p^2 = 2n^{2d}$ FLOPs per element in $d$ dimensions. But the basis is a tensor product,
$\phi_{ij}(\xi,\eta) = \ell_i(\xi)\,\ell_j(\eta)$, so

$$\partial_\xi u(\xi_i, \eta_j) = \sum_{k,l} u_{kl}\,\ell_k'(\xi_i)\,\ell_l(\eta_j) = \sum_k D_{ik}\, u_{kj}\qquad(\text{since } \ell_l(\eta_j) = \delta_{lj}).$$

The big matrix is the Kronecker product $I\otimes D$ and is mostly zeros: the derivative acts along one index at a time. Applying the small
$n\times n$ matrix $D$ to each of the $n^{d-1}$ lines of nodes costs $n^{d-1}\cdot 2n^2 = 2n^{d+1}$ FLOPs: sum factorisation.
The same trick works for interpolation to quadrature points and for the transposed (test-function) operations, and it is the reason high-order
tensor-product elements are affordable. On a GPU it also reduces the data each thread needs: a DOF reads one row and one column of its element, not the whole element.





Kernel fusion and occupancy


Each of our four kernels reads its inputs from global memory and writes its outputs back, and the next kernel reads them again. Since we are
memory-bound, the obvious optimisation is kernel fusion: one kernel per stage that computes volume and face terms and performs the RK update while
the values are still in registers. In the cost model (ideal caches, f32, $p=3$) the four separate kernels move 48 bytes per DOF and stage, a fully fused kernel
only 16 bytes (read $u$ and $k$, write $u^{\text{out}}$ and $k$), raising the intensity from about $0.68$ to about $2$ FLOP/byte — roughly a $3\times$ speed-up
for a memory-bound code. The price: each face flux is computed twice (once by each neighbour), the kernel needs more registers (lower occupancy), and the code
is harder to read. Production DG codes fuse aggressively and stage element data through workgroup memory; this chapter's solver deliberately keeps four
simple kernels that mirror the mathematics.

Single versus double precision, and CPU–GPU transfers


GPUs are fastest in f32; consumer GPUs run f64 at only a small fraction of the f32 rate, and WebGPU offers no f64 at all. Is f32 accurate enough? Each operation
has a relative rounding error of at most $2^{-24}\approx 6\cdot10^{-8}$. In an explicit scheme these errors are not amplified (the scheme is stable), they merely accumulate
slowly, so after hundreds of steps we expect differences from the f64 twin of order $10^{-7}$ to $10^{-6}$ relative to the solution — which is what the widget shows
(our tests require less than $2\cdot10^{-5}$ after 100 steps). This is far below the discretisation error of practical meshes
(at $p=3$ on a $32\times32$ mesh the $L^2$ error of the smooth test problem $\sin 2\pi x\,\sin 2\pi y$ at time $0.25$ is already below $10^{-6}$, and it decreases like $h^4$), so f32 suffices for this explicit
hyperbolic problem. It becomes inadequate when one needs errors near $10^{-7}$ relative, for long-time statistics with drifting invariants, or for
ill-conditioned implicit solves (the conditioning of elliptic matrices grows like $h^{-2}$ and eats digits); mixed precision (f32 work, f64 accumulation or residuals)
is the common compromise.


A second performance trap is the bus between CPU and GPU. A discrete GPU sits behind PCIe, whose bandwidth is more than an order of magnitude below
the GPU's own memory bandwidth, and every read-back forces the CPU to wait until the GPU has finished all queued work (a pipeline stall). The rule:
upload once, keep the data on the GPU, encode many steps per submission, and read back only what you need, rarely. Our widget reads back once per frame
for display; doing so after each step would make the GPU solver slower than the CPU for all but the largest meshes.




What goes wrong

    

  • Missing bounds check. The last workgroup is usually only partially filled; without if (g >= nDof) { return; } those threads write past the end of the
buffer (WebGPU clamps or discards out-of-bounds accesses, so you get silently wrong data rather than a crash).
    • 

  • Scatter-adds in parallel. "Each face adds its flux to both neighbours" looks innocent and gives wrong, non-reproducible results. Use a face buffer + gather, colouring,
or atomics.
    • 

  • Reading and writing the same buffer in one kernel when threads read neighbours' values: some threads see old, some new values. Use ping-pong buffers.
    • 

  • Uniform buffer layout. WGSL structs have alignment rules (e.g. a vec3<f32> is aligned to 16 bytes, uniform buffer offsets must be multiples of 256 bytes
on many devices). Mismatched offsets between the JavaScript ArrayBuffer and the WGSL struct give garbage constants without any error.
    • 

  • Timing the wrong thing. queue.submit() returns immediately; the GPU runs asynchronously. Measure from submission to
onSubmittedWorkDone() over a batch long enough that the fixed overhead is negligible.

Summary


    

  • GPUs maximise throughput: thousands of lanes, warps executing in lockstep (SIMT), latency hidden by keeping many warps resident (occupancy).
    • 

  • Divergent branches cost the sum of both paths for a warp; one thread per DOF gives plenty of parallelism with little divergence for DG.
    • 

  • Explicit DG kernels have low arithmetic intensity (well below 10 FLOP/byte): they are memory-bound, so coalesced SoA layouts and fewer bytes (fusion) matter more than FLOPs.
    • 

  • DG maps well to GPUs: element-local dense work, coupling only through faces, diagonal mass matrix, explicit stepping. CG assembly races and implicit solves need more care.
    • 

  • Parallel scatter-adds race. Cures: a face buffer written once per face and gathered per element, graph colouring, or (integer/emulated) atomics.
    • 

  • Sum factorisation reduces element operator cost from $O(p^{2d})$ to $O(p^{d+1})$ for tensor-product bases.
    • 

  • f32 is sufficient for explicit hyperbolic DG at moderate accuracy; keep data on the GPU and read back rarely.
